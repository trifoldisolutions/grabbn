## Revised Implementation Plan

### Phase 1 — Schema additions (`server/models/bucket.js`)
Zero risk, non-destructive. Unscored docs default to 0 and rank last until first job run.

```js
exploreScore:          { type: Number, default: 0, index: true },
exploreScoreUpdatedAt: { type: Date,   default: null },
topic:                 { type: String, default: null, index: true },
directViewCount:       { type: Number, default: 0 },        // organic views only (explore-driven excluded)
verifiedShareCount:    { type: Number, default: 0 },        // arrivals via ?ref=share
skipCount:             { type: Number, default: 0 },        // "not interested" signals
```

`topic` = primary domain of the bucket, derived by `buildExploreScores` in priority order:
1. `sourceUrl` (curator-declared)
2. Pinned link's domain
3. Link with the highest `clickCount`
4. First link in the array

Leading `www.` is stripped. If no URL can be parsed, `topic` stays `null`.
A bucket's topic can shift over time as links are pinned or accumulate clicks — each change
re-slots it into a different ranking context, improving organic discoverability.

Add compound index: `{ isPublic: 1, exploreScore: -1 }`

### Phase 3 — Score job (`server/jobs/buildExploreScores.js`)
Streams a cursor over all public buckets, computes score and topic, writes back via `bulkWrite`
in batches of 500. Then runs a second aggregation pass to build `TopicScore`. Runs every
**2 hours** (staggered from `buildRepositories`).

```
exploreScore =
  max(0,
    log(grabbedBy.length + 1) × 2.0        ← intentional curation
  + log(Σ links[].clickCount + 1) × 0.8    ← active engagement
  + log(directViewCount + 1) × 0.3         ← organic reach (explore views excluded to avoid circular feedback)
  + log(verifiedShareCount + 1) × 0.5      ← confirmed distribution (landing via shared link)
  + min(hashtags.length × 0.1, 0.5)        ← topic diversity bonus
  - log(skipCount + 1) × 1.2               ← "not interested" penalty
  ) × recencyDecay(createdAt, halfLife=30d) ← exponential decay, floor 0.1
  + coldStartBoost(createdAt)               ← additive boost: 1.5 at day 0, tapers to 0 by day 7
```

**Signal notes:**
- `viewCount` is kept for display only. `directViewCount` (views NOT from the explore feed) is
  used in the score to break the circular feedback loop where explore impressions inflate future ranking.
- `verifiedShareCount` replaces `shareCount` in the score. It counts arrivals via `?ref=share`
  rather than button clicks — a confirmed real-world distribution event.
- `skipCount` is a log-scaled penalty weighted above views but below grabs, reflecting that a
  skip is a softer rejection signal than a grab is a positive one.
- `coldStartBoost` is additive (applied after decay) so it gives new buckets a floor to compete
  without inflating the score of buckets that already have organic traction.

`totalLinkClicks` is computed inline via `{ $sum: '$links.clickCount' }`.
`grabbedBy.length` replaces the non-existent stored `grabCount`.

### Phase 3b — Topic scores (`server/models/topicScore.js`)
A `TopicScore` document is upserted per domain at the end of every score job run:

```js
{
  domain:      String,   // "github.com"
  score:       Number,   // Σ exploreScore of all public buckets with this topic
  bucketCount: Number,   // number of contributing buckets
  updatedAt:   Date
}
```

`score` captures overall engagement weight for the domain this cycle.
Only domains with `bucketCount >= 3` are used for cold-start recommendations
(avoids surfacing statistically meaningless single-bucket topics).

Topics are domain-scoped (not global free-text), which bounds cardinality and eliminates
noise hashtags. Over time, the system can surface common hashtags per domain as suggestions.

### Phase 4 — `/api/v2/explore` endpoint (`serve.js`)
Two-phase: fetch top `limit × 5` candidates by `exploreScore` (compound index, fast), then
re-rank in-memory for authenticated users using 3 personalization signals:

| Signal | Weight | Source |
|---|---|---|
| Hashtag overlap with user's grabbed buckets | ×1.5 per match | `Bucket.hashtags` |
| Domain affinity (domains user clicked recently) | ×0.4 per click | `LinkClick` aggregate, 30-day window |
| Social proximity (grabbed by someone you follow) | ×1.3 multiplier | `grabbedBy` × `Subscription` |

Social proximity uses `×1.3` multiplier (not flat `+3`) to prevent a single prolific follower
from flooding the top. Anonymous users get candidates sorted by raw `exploreScore` only.

Pagination uses `skip` offset (scores are stable between 2h job runs, so drift is acceptable).

### Phase 5 — Rebuild Showroom as personalized feed (`serve.js`, showroom endpoint)

#### Registered users (follows/grabs exist)
Change the flat `Bucket.find()` to a personalized query:

1. Resolve followed curator IDs via `Subscription.find({ followerId })`
2. Resolve grabbed source bucket IDs via `Bucket.find({ userId, sourceBucketId: { $ne: null } })`
   — also select `createdAt` (= grab time) for each copy
3. `$or` filter: `userId: { $in: followedIds }` OR per-grabbed-bucket condition
   `{ _id: sourceId, updatedAt: { $gt: grabTime } }` — **exclude grabbed source buckets that
   have not been updated since the user grabbed them**
4. Sort `updatedAt: -1` — surfaces new buckets from curators you follow and updates to grabbed buckets
5. **Fallback** for zero follows/grabs: fall through to global `exploreScore`-ranked feed

Remove the 4 filter buttons (Category, Collection, Price Range, Activeness) from `showroom.ejs`.

#### Anonymous / guest users — cold-start → warm-start progression
Guest users have no history, so recommendations bootstrap from platform-wide topic signals
and shift to personalized as engagement accumulates.

**Cold start** (default for new guests):
- Query `TopicScore` for the best-performing domain this week (`bucketCount >= 3`)
- Serve the top-scored buckets within that domain sorted by `exploreScore`
- If no topic scores exist yet (first job run pending), fall back to global `exploreScore` ranking

**Warm start** (triggered after engagement threshold):
- Show buckets from the guest's `inferredTopic` sorted by `exploreScore`
- Reserve **1 slot per page** for a discovery bucket from the second-best topic
- Discovery slot uses a gentle `skip` offset across pages for variety

**Guest session state** (stored on the `User` document — survives session-to-account conversion):
```js
guestSession: {
  inferredTopic:    String,   // domain with most accumulated points
  points:           Number,   // total weighted engagement
  topicEngagements: [{ domain, pts }],  // per-domain breakdown (array avoids dot-in-key issues)
  activeMinutes:    Number,   // combined browsing time (idle gaps > 30 min excluded)
  lastActiveAt:     Date,     // timestamp of last engagement event
  warmStart:        Boolean   // true once warm threshold is crossed
}
```

**Point weights:**
| Action | Points |
|---|---|
| Grab | 4 |
| Share | 5 |
| Page visit (bucket view) | 1 |
| Link click | 0.5 |

**Warm-start threshold:** ≥ 10 points within 6 hours of **combined active time**
(not 6 hours from first interaction — idle gaps > 30 min do not count toward the window).

**Reset condition:** if 6 hours of active time are exhausted before 10 points are reached,
the session resets to cold-start. The user stays low-engagement — cold-start remains appropriate.

**Session migration:** since anonymous users are persisted as `User` documents with `isAnonymous: true`,
converting to a registered account (`convertToRegistered`) preserves `guestSession` fields intact.
No migration step needed.
