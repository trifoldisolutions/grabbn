HIGH RISK
H1 — Chargeback / Fraud Prevention (new layered system)
What: Multiple rules that restrict new accounts from doing maximum damage with a stolen card.

Implementation touches:

server/config.js — add FRAUD_RULES tiers
server/models/user.js — add fields: firstPurchaseAt, dailyUnlockSpend, dailyUnlockResetDate, dailyPurchaseCount, dailyPurchaseResetDate, pendingCredits, pendingCreditsUntil
server/routes/credits.js (topup) — enforce Rules 1, 3, 4, 5
server/routes/credits.js (unlock) — enforce Rule 2 + pending credits check
Rules:

Rule	Description
R1	Purchase cap per transaction based on account age tier
R2	Daily unlock spend cap based on account age tier
R3	First purchase held 24h before becoming spendable
R4	Max N credit purchases per 24h rolling window
R5	Cumulative purchase cap in first 14 days
H2 — Untracked credit liability
What: No way to know total credits in circulation = hidden cash obligation.

Implementation touches:

serve.js or admin route — add GET /api/admin/liability that aggregates db.users.sum(credits) + db.users.sum(pendingCredits)
H3 — No refund mechanism
What: If Stripe auto-reverses a payment after credits are spent, no path to claw back curator credits.

Implementation touches:

server/routes/credits.js (webhook) — handle charge.dispute.created Stripe event: if credits are still pending → zero them out; if already spent → flag account for manual review, log the loss
server/models/user.js — add flagged: Boolean field
MEDIUM RISK
M1 — Platform fee logged to wrong userId
What: platform_fee transactions are stored under bucket.userId (the curator), making revenue reporting impossible.

Implementation touches:

server/routes/credits.js (unlock) — change platform_fee transaction to use a dedicated platform account ID instead of bucket.userId
server/models/user.js — seed a platform wallet user on startup, store its _id in config
M2 — No platform fee revenue tracking
What: Can't answer "how much has the platform earned total in fees?"

Implementation touches:

server/models/user.js — platform wallet user accumulates credits from every unlock
serve.js or admin route — GET /api/admin/revenue returns platform wallet balance + transaction history
Depends on: M1 being implemented first.

LOW RISK
L1 — Bucket deleted after viewer paid to unlock it
What: Curator deletes a bucket, viewer loses access but curator keeps the credits.

Implementation touches:

serve.js (bucket DELETE route) — check if bucket has any BucketAccess records before allowing deletion; either block deletion or refund affected viewers' credits
L2 — Free/promotional credits = unbacked liabilities
What: If you ever issue free credits for marketing, they can be spent on unlocks, forcing curator payouts with no cash backing.

Implementation touches:

server/models/user.js — add bonusCredits field (separate from paid credits)
server/routes/credits.js (unlock) — spend credits (paid) before bonusCredits, so curators only get paid from real-money credits
server/config.js — add BONUS_CREDITS_SIGNUP constant
